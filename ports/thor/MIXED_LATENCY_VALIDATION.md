# 混合五路时延修复（2026-10-18）

## 测量口径

双 Thor，两个固定静态矿井画面、两个循环动态矿井视频、一路实时计时器，
均为 1920×1080、12 FPS。五个独立上下文，TensorRT FP16，QP=11、GOP=96、
reset=32、运动预取=1、熵 worker=1，NVDEC 输入、NVENC 运动代理及重建发布。
模型、引擎、量化参数和输入输出帧率未变，没有使用抽帧或接收丢帧追赶。

下列毫秒统计延续历史口径：**编码板 NVDEC 帧就绪 → 编码板收到解码完成回执**。
它不包含 NVDEC 之前的缓冲、源端采集/编码、NVENC 发布完成或播放器显示。
接收等待与帧处理分别在解码板同一单调时钟上计算；网络部分用往返差值计算，
不依赖双板墙钟同步。前 96 帧约 8 秒单列为启动窗口。

## 积压在哪里

混合场景 780 帧/路复现中，平均总时延为 1879 ms，P95 3512 ms，最大 3890 ms。
时延随运行增长，接收队列最高 39 帧。稳定窗口的平均分解为：

| 阶段 | 修复前 ms | 最终长测 ms |
|---|---:|---:|
| NVDEC 就绪到语义首包发送 | 243.4 | 96.2 |
| 同帧分片发送 | 0.94 | 0.87 |
| 解码板末包接收到帧处理开始 | 1548.4 | 12.1 |
| 解码帧处理（含 GPU 调度、参考更新及输出入队） | 86.4 | 20.9 |
| 余下网络及回执 | 0.25 | 0.20 |

主要积压在解码板等待 GPU 消费；原平均帧处理 86.4 ms 超过 12 FPS 的
83.3 ms 帧间隔。五个上下文同时运行整帧图，以及 CPU 张量上传时的同步暂存和
重复复制，使这套工作负载缺少实时余量。混合源和实时计时器增加了输入节奏及
硬件负载的变化，触发了积压；不能解释为语义码率变高导致网络慢。
此处“资源争用”由同场景调度对照支持，未声称用 Nsight 分清了缓存与带宽的占比。

## 修改

1. 共享引擎的多上下文模式，按 GPU 设备串行执行单次模型调用，包括输入绑定、
   模型运行和输出完成。五路保留各自的上下文、CUDA stream、参考状态和协议会话；
   采集、运动代理、CPU 熵处理、NVENC 和网络仍可并行。新增
   `model.<模型>.scheduler_wait_wall`，将调度等待与模型自身执行时间分开。
   batch5 的批量调度路径保持原状。诊断变量 `MLVC_THOR_SERIAL_INFERENCE=0`
   可关闭此项，正常启动不需要设置变量。
2. Thor 的 CPU 输入直接由 TensorRT 在本路计算流上上传到固定模型缓冲，
   去掉通用 workspace 中“同步 H2D 暂存 → 模型内再 D2D”的路径和不再需要的
   输入暂存分配。真实 GPU 输入仍保持设备驻留；运行函数返回前仍等待输出完成，
   不延长借用 CPU 指针的生命周期。Ascend 路径保持原逻辑。
   `MLVC_THOR_DIRECT_HOST_INPUT=0` 仅用于新旧路径对照。
3. 实时输入声明无 B 帧时，给 CUVID 设置 `AV_CODEC_FLAG_LOW_DELAY`；声明有
   B 帧的流保留重排路径。未启用会丢掉探测包的 `AVFMT_FLAG_NOBUFFER`，
   也没有跳过参考帧。原 CUVID 的显示等待发生在 NVDEC 帧就绪之前，历史内部
   回执指标没有包含它，所以单看约 130 ms 不能代表画面读数差。

[FFmpeg 6.1.1 CUVID 源码](https://github.com/FFmpeg/FFmpeg/blob/n6.1.1/libavcodec/cuviddec.c#L944)
将该标志映射到显示延迟 0，默认值为 4 帧；
[NVIDIA API 说明](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html)
说明 `ulMaxDisplayDelay=0` 无额外显示等待。12 FPS 下四帧预算约 333 ms，
实际画面改善还取决于播放器、帧相位及其他缓冲。

## 同长度短轮对照

各轮均为真实混合源，每路 780 帧、五路共 3900 帧完整，剔除每路前 96 帧。
输入发布保持在编码板，计时器仍使用该板的 NVENC。

| 版本 | 平均 ms | P95 ms | 最大 ms | 时延标准差 ms |
|---|---:|---:|---:|---:|
| 修复前 | 1879.3 | 3511.8 | 3890.4 | 878.6 |
| 仅调整模型调度 | 127.7 | 162.0 | 271.7 | 17.3 |
| 仅去掉输入重复上传 | 149.7 | 205.8 | 389.7 | 30.0 |
| 两项组合 | 129.5 | 164.3 | 361.4 | 18.4 |

另做过回放计时器和五路动态的探索轮；它们不属于同一混合工作负载，
未用于上表。五路动态探索轮与一次编译有重叠，不作为性能结论。

## 五路长测

先用严格完整帧接收策略验证，再使用生产的 64 帧队列和 recover 策略复测，
最后加入 CUVID 低延迟设置再做完整长测。每轮每路 3120 帧，约 260 秒。

| 阶段 | 接收策略 | 平均 ms | P95 ms | 最大 ms | 时延标准差 ms |
|---|---|---:|---:|---:|---:|
| GPU 调度与拷贝修复 | 严格验帧 | 138.5 | 178.3 | 396.9 | 23.3 |
| GPU 调度与拷贝修复 | 生产配置 | 132.3 | 158.5 | 404.4 | 16.9 |
| 最终版，含 CUVID 调整 | 生产配置 | 130.3 | 160.8 | 366.0 | 17.5 |

表中为剔除前 96 帧的统计。**最终版包含启动阶段时，平均 130.8 ms、最大
432.2 ms，最大值在第三路第 2 帧。** 相邻帧时延差的绝对值均值为 13.4 ms、
P95 50.2 ms；它与表中的时延标准差是不同指标。

最终版分路结果如下，增长为最后 120 帧均值减最初稳定窗口 120 帧均值：

| 通道 | 平均 ms | P95 ms | 最大 ms | 时延标准差 ms | 编码 FPS | 解码回执 FPS | 前后增长 ms |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1（静态） | 131.1 | 154.4 | 366.0 | 17.2 | 11.996 | 12.004 | -2.1 |
| 2（静态） | 132.5 | 156.1 | 364.3 | 18.0 | 11.996 | 12.003 | +1.0 |
| 3（动态） | 137.8 | 172.3 | 246.3 | 17.5 | 11.996 | 12.000 | +0.4 |
| 4（动态） | 129.6 | 157.6 | 242.1 | 15.5 | 11.996 | 12.000 | -3.0 |
| 5（计时器） | 120.4 | 154.5 | 243.3 | 14.3 | 11.995 | 12.001 | -2.6 |

三轮长测共 **46,800 帧**全部编码、收到回执、解码并发布；RTP 丢包、CRC 错误、
接收溢出、依赖缺口、跳帧和发布丢帧均为 0。逐路 RTP 序号连续、帧时间戳步长
7500（90000/12），净载荷字节计数在发送端、接收端和观察记录中一致。
输入 PTS 严格递增，最终长测各路相对积压变化约 -7.8 至 +0.14 ms，未持续增长。
最终版全程队列最高 6 帧，包含启动阶段；不宣称始终没有任何在途帧。
另外已部署的 GPU 修复版在正式 `bin/` 位置完成每路 780 帧启动检查。

## 计时器画面抽查

在同一台 Windows 电脑上并行接收原图 `input4` 与重建 `five-out4`，
两个独立解码线程始终消费帧，在同一次采样中保存各自最新图像。
RTSP 使用 TCP，客户端关闭额外缓存并限制单个解码线程。

- CUVID 调整前：原图 52.167 秒、重建 51.667 秒，读数差 500 ms。
- CUVID 调整后第一次：原图 81.167 秒、重建 80.917 秒，读数差 250 ms。
- 调整后第二次：原图 219.667 秒、重建 219.417 秒，读数差 250 ms。

截图和到达时间在本地 `artifacts/mixed-latency-20261018/timer-probe-*/`。
12 FPS 的粒度约 83 ms；两路最新帧到达并非同一瞬间，因此这些是画面抽查，
不是连续端到端时延分布，也不等同于相机曝光到屏幕的绝对总时延。
浏览器的 WebRTC 自适应缓冲还可能增加延迟。用 UI 对比时先把原图补偿设为 0，
原有 200 ms 补偿会改变可见读数差；本次没有修改用户的 UI 配置。

## 功能与帧序验证

- 原生 CTest 15/15，通过硬件输入、颜色/填充、帧率采样和 RTP/恢复等检查。
- 三个真实模型、各 4 个有效输入样本，普通提交与图重放输出逐字节一致。
  生产 workspace 的旧暂存路径和新直接输入路径也各做 4 样本逐字节对照。
- 使用 NVENC 生成带 B 帧的 1080p/12 FPS 视频。96 帧文件读取作为参考，
  RTSP 读取 48 帧；每帧可见 NV12 像素和 FP16 预处理结果逐字节一致，
  PTS 严格递增。此流报告 `has_b_frames=1`、`input_nvdec_low_delay=0`，
  保留重排；无 B 帧的五路长测中均为 `input_nvdec_low_delay=1`。
  可在解码板构建 `probe_nvdec_surfaces` 后，运行
  `python3 src/MLVC/ports/thor/tools/check_live_b_frames.py --rtsp-base rtsp://192.168.5.3:8554`
  重新生成硬件测试视频并验证，输出保存在带时间编号的 `logs/b-frame-regression-*/`。
- 五路基准工具的 3 项测试、修改文件的 clang-format、Python 语法及 diff 检查通过。

## 部署与复现

最终程序和源码已同步到两块板的 `/home/xidian/workspace/MLVC_Thor/`。
模型、引擎和五路生产配置校验值不变。正常启动命令不变：

```bash
# 编码板，单独终端提供五路源
cd /home/xidian/workspace/MLVC_Thor
bash scripts/run_test_sources.sh

# 解码板
cd /home/xidian/workspace/MLVC_Thor
bash scripts/run_five.sh decode contexts

# 编码板，另一个终端
cd /home/xidian/workspace/MLVC_Thor
bash scripts/run_five.sh encode contexts
```

MediaMTX 由使用者启动。测试脚本可在本机仓库运行，先关闭占用同一 RTP 端口和
RTSP 路径的其他编解码/测试源；脚本只停止自己记录的进程：

```powershell
python ports/thor/tools/benchmark_mixed.py --label mixed-check-20261018 --frames 3120 --output artifacts/mixed-check --rtsp-base rtsp://192.168.5.3:8554 --live-receiver
python ports/thor/tools/analyze_five_latency.py artifacts/mixed-check/mixed-check-20261018.json
```

编码板/解码板 SSH 地址、运行根目录与可执行目录分别可通过 `--encoder`、
`--decoder`、`--root`、`--binary-dir` 指定。`--legacy-gpu-path` 只用于关闭
前两项修复的诊断对照。观察器 `trace_rtp.c` 从随附源文件编译，不依赖历史归档。

本次证据在本地 `artifacts/mixed-latency-20261018/`，包括每轮配置、双板日志、
逐帧分解、连续性/字节对账、模型与 B 帧验证和最终部署 SHA-256。

构建统一使用 `src/MLVC` 和 `build`，不恢复重复源码目录。
