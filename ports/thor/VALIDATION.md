# 双板验证记录：2026-10-14

编码板 192.168.5.16（序列号 1614525610211），解码板 192.168.5.17（序列号 1614525610151），均为 NVIDIA Jetson AGX Thor。输入视频为使用者提供的 `614lab.mp4`，1920×1080，30 FPS，共 537 帧。

参数：QP 11、GOP 96、参考重置间隔 32、translation warp 开启、LTR 关闭。三个模型来自同一套经 SHA-256 审计的原始 ONNX；两块板使用相同 TensorRT 引擎和 manifest。

| 验证链路 | 帧数 | 编码 FPS | 解码 FPS | 结果 |
|---|---:|---:|---:|---|
| FP16 文件，软件运动代理基线 | 104 | 14.74 | 63.04 | 全部通过 |
| FP16 文件，NVENC 运动代理 | 104 | 38.28 | — | 编码通过 |
| 离线视频→文件→另一块板解码 | 537 | 41.92 | 67.23 | 全部通过 |
| 离线视频→RTP→另一块板解码 | 537 | 47.01 | 53.11 | 全部通过 |
| RTSP 输入→RTP→解码→NVENC RTSP 输出 | 900 | 30.46 | 31.74 | 900 帧全部发布，输出丢帧 0 |
| 最终脚本：离线视频→RTP→NVENC RTSP 输出 | 537 | 40.59 | 45.22 | 537 帧全部发布，输出丢帧 0，EOS 后正常退出 |

FPS 为程序报告的处理帧率，不包括引擎加载、输入打开。RTSP 测试包括实时输入等待；离线测试尽快读取文件。没有通过降低分辨率或跳帧提高帧率。GPU 时钟和后台负载会影响结果，本记录不承诺所有视频均达到同一速度。

FP16 首轮还保存了 4 帧重建张量，全部为有限数值且在 [0,1] 内；重建 PNG 和实际 RTSP 接收截图已检查，画面正常。

优化包括：NVENC 单参考、无 B 帧及无 lookahead 的运动代理；CUDA BT.709 YUV444 FP16 预处理及边缘补齐；最多 4 帧的视频读取队列；复用 CUDA 预处理缓冲；原有有界运动预取与熵编解码队列；CUDA NV12 转换和异步 NVENC 发布。保留 `motion_backend="libx264"` 作为可选软件路径。

异常验证：

- RTSP TCP 服务接受连接但不回应：约 4.08 秒报错退出，包含模型加载和 3 秒打开超时。
- 发布端中断：约 0.67 秒报错退出，明确提示断流/读取超时。
- CTest 11/11 通过，包含 GPU 色彩转换、边缘/stride 补齐、空帧槽分配、视频顺序和 EOF、RTP/RTCP、码流、模型完整性及参考平移验证。
- 最终 Linux 启动脚本通过语法检查；两块板的库依赖和模型 SHA-256 检查通过。

摄像头按使用者要求未做实机测试。未启动或修改使用者的正式 MediaMTX/UI；RTSP 测试使用独立端口 18554 的临时 MediaMTX，完成后停止。

原始日志、重建截图和 JSON 汇总保存在 Windows 的 `MLVC_310P1/artifacts/thor-20261013`；板卡日志保存在各自运行目录的 `logs/`。


## 可配置抽帧验证

新版编码端默认 `target_fps=30`，可改为 25，0 表示禁用。采样基于媒体声明/摄像头协商的输入帧率，按源时间均匀选择，不受离线解码速度影响。输出标称帧率、运动代理、码流及解码输出使用抽帧后的帧率；低于目标的输入全部保留、不补帧。FP16 验证数据不抽帧。

| 输入 | 目标 | 编码/解码结果 |
|---|---:|---|
| 60 FPS 离线文件，120 帧 | 30 FPS | 60 帧全部编码并在另一块板解码 |
| 同上 | 25 FPS | 50 帧全部编码并在另一块板解码 |
| 60 FPS RTSP 输入 | 30 FPS | 120 帧全部经 RTP 解码，码流帧率 30 |
| 60 FPS RTSP 输入 | 25 FPS | 100 帧全部经 RTP 解码，码流帧率 25 |

更新后 CTest 12/12 通过，包含 60→30、50→30、30→25、59.94→30、120→25、25→30、15→30、相同帧率、禁用采样，以及真实视频取帧顺序、EOF 和像素验证。摄像头实机测试仍未进行。

## 编码端 GPU 数据路径与运动代理优化

后续基准使用三轮相同离线文件和三轮实时 RTSP；最终版本离线每轮 537 帧、实时每轮 300 帧全部编解码，实时每轮输出丢帧 0。运动估计由约 20 ms 降到离线 14.89 ms、实时 13.11 ms；离线编码吞吐 42.68→43.66 FPS。实时编码侧 ready-to-output 71.12→57.32 ms，双板回执平均延迟 226.59→208.58 ms。离线 P95 回执延迟 440.94→491.06 ms，仍有尾延迟问题。

这组数据排除引擎启动，延迟样本与 FPS 排除前 96 帧，解码程序固定；回执边界不包含实际 RTSP 发布完成和浏览器显示。最新 CTest 12/12 通过；原业务解码程序验证 537 帧及 60/50 帧抽帧码流全部通过。34 帧抽样平均 Y-PSNR 31.1852→31.1843 dB。完整测量方法、逐步骤耗时、兼容性及限制见 [OPTIMIZATION.md](OPTIMIZATION.md)，先前历史记录保留，不将不同测试配置的单次 FPS 直接视为优化收益。

后续逐模块计时发现并修正命令行入口始终绑定 CPU 输出的问题，GPU 参考缓存此前未实际生效。修正后，三次 MP4 编码均值 43.51 FPS、FP16 69.67 FPS；瓶颈分别为视频读取线程 22.92 ms、主编码流程 14.20 ms，对应理想流水线约 43.63 / 70.43 FPS。两种输入各三次完整 537 帧输出与修正前逐比特一致，两种输入 RTP 537 帧联调均全部通过；CTest 12/12 通过。详见 OPTIMIZATION.md 的后续更正与模块表。
