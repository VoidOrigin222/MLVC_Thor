# 编码端优化与双板联调：2026-10-14

最新 MP4 NVDEC 路径及并发像素一致性修复见 [NVDEC_VALIDATION.md](NVDEC_VALIDATION.md)：编码三轮平均 69.77 FPS，GPU 利用率 92.9%，六次完整输出码流逐比特相同。下面保留此前软件 MP4 输入的历史结果。

编码板 `192.168.5.16`，解码板 `192.168.5.17`，NVIDIA Jetson AGX Thor。输入 `614lab.mp4`，1920×1080，模型输入保持 `[1,3,1088,1920]` FP16。QP 11、GOP 96、重置间隔 32，LTR 关闭。模型、分辨率、抽帧策略、传输配置和解码端业务程序保持一致。

**后续计时更正：** 首轮程序的 `apps/encode_main.cc` 始终传入 CPU 输出模式，导致写好的 GPU 参考缓存没有被命令行程序实际使用。因此下面首轮性能表不能用于证明 GPU 参考缓存的收益。现已修正入口，依据 `input_device_resident` 选择输出绑定；最新逐模块结果见文末。前面的三轮测量日志保留，数据本身有效。

## 已实施的变化

- 将运动估计拆为 CUDA NV12 转换、NVENC 输入复制、NVENC 编码、H.264 包校验/准备、H.264 软件解码、运动向量归约，各项输出平均耗时；原有整体运动耗时和队列等待计时保留。
- 视频/RTSP/摄像头预处理结果以 GPU FP16 张量交给编码器，每个输入槽拥有独立显存和生命周期。去掉 FP16 图像下载到 CPU 后再次上传的路径。图像有 12,533,760 字节，因此每帧少一次该大小的 D2H 和 H2D。
- GPU 上转换运动代理 NV12，通过 FFmpeg CUDA 硬件帧送入 NVENC，去掉 CPU FP16→NV12 转换和 NV12 图像在 GPU/CPU 间往返。仍保留约 3 MB 的 GPU 内部复制，因为 NVENC 输入需要独立、可复用的表面。
- 编码器参考特征、重置图像留在 GPU；参考平移在 CUDA 上执行，并逐字节验证边界与 CPU 实现相同。参考缓冲复用，避免每帧显存申请/释放引发同步。熵编码所需的模型输出仍下载到 CPU，H.264 压缩包仍交由 CPU 软件解码以提取运动向量。
- NVENC 运动代理使用四个 slice，软件解码使用四个 slice 线程，不使用引入跨帧等待的 frame threading。`motion_decode_threads=1` 可恢复单 slice。GPU 路径可通过 `input_device_resident=false` 关闭。

## 对比方法与结果

每组运行三次，离线每次 537 帧，实时 RTSP 每次 300 帧，均完整接收、解码。实时各次发布 300 帧、输出丢帧 0。性能 FPS 和双板延迟样本排除前 96 帧；下面的延迟 P95 是三次各自 P95 的平均值。运动子步骤和编码侧 ready-to-output 计时是程序整轮均值，包含预热帧。GPU 时钟和后台负载没有通过 sudo 强制锁定。

基线是优化前保留的编码程序，仅添加相同计时点；解码测试统一使用保留的基线解码程序加可关闭的回执探针。离线比较使用同一文件和完整帧序列。实时测试将文件循环发布为 30 FPS RTSP，三轮取到的片段不完全相同，因此实时差异是重复测试的观察结果，并非逐帧配对实验。临时 MediaMTX 使用独立端口 18554，未修改正式服务。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 离线编码吞吐 | 42.68 FPS | 43.66 FPS | +2.3% |
| 离线整体运动估计 | 20.05 ms | 14.89 ms | −25.7% |
| 离线编码侧 ready-to-output | 72.09 ms | 59.00 ms | −18.2% |
| 离线双板回执平均延迟 | 249.53 ms | 228.77 ms | −8.3% |
| 离线双板回执 P95 | 440.94 ms | 491.06 ms | **+11.4%，尾延迟未改善** |
| 实时编码吞吐 | 29.86 FPS | 29.94 FPS | 输入约束为 30 FPS |
| 实时整体运动估计 | 20.43 ms | 13.11 ms | −35.8% |
| 实时编码侧 ready-to-output | 71.12 ms | 57.32 ms | −19.4% |
| 实时双板回执平均延迟 | 226.59 ms | 208.58 ms | −18.02 ms（−8.0%） |
| 实时双板回执 P95 | 261.01 ms | 237.82 ms | −23.19 ms |

**这次主要改善运动估计耗时和编码侧延迟，吞吐增幅较小。离线尾延迟仍有波动，不能宣称整体抖动已经解决。** 离线三次优化后 FPS 分别为 43.99、43.94、43.05，基线为 42.38、43.11、42.55；样本有限，2.3% 增幅不能当作固定性能保证。

运动估计子步骤，单位 ms/帧：

| 子步骤 | 离线前 | 离线后 | 实时前 | 实时后 |
|---|---:|---:|---:|---:|
| CUDA FP16→NV12（新增 GPU 路径） | — | 1.23 | — | 0.80 |
| NVENC 输入填充 | 0.26 | 0.21 | 0.30 | 0.07 |
| NVENC 编码 | 7.02 | 6.84 | 5.73 | 5.58 |
| H.264 包校验/准备 | 0.25 | 0.30 | 0.30 | 0.32 |

子步骤不覆盖旧路径全部 CPU 转换、调度和函数开销，不能将各行之和当作完整运动估计计时。NVENC 计时是同步 API 的墙钟耗时，包含等待，不是硬件纯计算时间。GPU 输入的实测日志为 `input_fp16_d2h_bytes=0`、`input_x_h2d_bytes=0`，后者仅统计 TensorRT runtime 对主输入 x 的上传。

## 延迟的测量边界

编码板在选中源帧的 BGR 读取/解码完成时记录单调时钟。解码板完成该帧语义解码、参考更新并将 RTSP 输出入队后，回传带帧号的 UDP 回执；编码板记录到达时间。两端时间都使用编码板的同一时钟，因此不依赖板间时钟同步。

双板回执延迟包含输入预处理、队列、运动估计、语义编码、熵编码、RTP 传输、解码和回执返程。**不包含摄像头曝光/源端 RTSP 编码，也不等待解码端 NVENC 实际完成发布，不包含浏览器播放、缓冲和显示延迟。** 编码侧 ready-to-output 从 FP16 输入准备完成到文件写入或 RTP 输出入队，边界与双板指标不同。

## 验证及兼容性

- CTest **12/12** 通过，包括 CUDA 颜色/补齐、GPU 参考平移、输入槽独立所有权/复用/关闭后的生命周期、采样顺序、RTP/RTCP、码流和模型校验。
- 最终编码程序生成完整 537 帧码流，并由原业务解码程序全部解码；60 FPS 输入的 30/25 FPS 模式分别得到 60/50 帧，另一块板全部解码。
- CPU 回退加单 slice 的完整码流 SHA-256 与旧版相同：`330ff9234ebd684e172c6a9ae74a10111cc755cfac021afe9cee82bb664d132e`。
- 最终 GPU 四 slice 码流 SHA-256：`1fe56b70546d181181729b1e757c47d7e2639526cc4436ebfd2a3cc0113afb89`。只改变数据路径、保留单 slice 的 GPU 版本与旧码流相同；四 slice 会轻微改变运动向量，**不保证与旧版逐比特相同**。
- 完整视频每 16 帧抽取一帧，共 34 帧重建质量验证：旧版平均 Y-PSNR 31.1852 dB，新版 31.1843 dB，差值 −0.0009 dB；单个样本最差变化 −0.2899 dB。这是回归验证，不是在运行中按 PSNR 控制码率/质量，也不能代表所有视频。
- 摄像头按原要求未做实机测试，离线和 RTSP 已测试。解码端业务可执行文件保持原版本，SHA-256 `afe78b7f4cd3b27b8dc288fd921dbc489267cceb89c460ed9b14273212fb514a`。

## 仍需优化的部分

最终一轮离线 profile 中，主编码模型 stage 约 13.90 ms/帧，熵编码约 5.64 ms/帧，运动估计仍约 14.69 ms/帧。流水线阶段重叠，不能将耗时简单相加或取倒数预测 FPS。输入 `video.read.frame` 约 15.66 ms，包含读取队列等待，需进一步拆分读取、视频解码、上传和 CUDA 转换后才能归因。此次 GPU/CPU 拷贝减少没有等比例提升吞吐，当前不能将全部瓶颈归于数据搬运。

解码端当前熵解码窗口满 4 帧才弹出旧帧，按代码路径推断实时 30 FPS 可能引入约 4/30 秒的等待；这是下一阶段降低端到端延迟的重要候选，本次未改变解码策略。离线 P95 波动也需继续从有界队列、接收窗口和运行时调度分析。

## MP4 / FP16 逐模块计时与理论编码 FPS

本轮使用完整的同一段 537 帧视频；MP4 为 HEVC Main 10、1920×1080、YUV420 10 bit，FP16 提前转换为 BT.709 YUV444、1088 行边缘补齐。两条路径均 `target_fps=0`，各三次，编码和多数模块计时排除前 96 帧。FP16 的 CPU NV12 准备暂用程序整轮平均，其余表中连续模块是 441 帧的均值。FP16 文件读测试为系统缓存热态。所有六次输出的 SHA-256 均与各自修正前的完整码流相同。

| 模块（ms/帧） | MP4 | FP16 | 执行位置 / 边界 |
|---|---:|---:|---|
| 压缩数据读取与视频解码 `grab` | 9.45 | — | 视频读取线程，CPU 后端 |
| 取出图像并转换为 BGR `retrieve` | 13.47 | — | 同一个视频读取线程 |
| **视频读取线程连续工作合计** | **22.92** | — | 上面两步串行，不含队列等待 |
| BGR 上传与 FP16 预处理合计 | 0.65 | — | 输入准备线程，已扣除等待视频队列的时间 |
| 其中 BGR 上传 CUDA stream 时间 | 0.23 | — | 包含在预处理合计中 |
| 其中 CUDA BGR→FP16 时间 | 0.22 | — | 包含在预处理合计中 |
| FP16 文件读取 | — | 2.26 | CPU / 文件缓存 |
| FP16→运动代理 NV12 准备 | — | 6.24 | 与 FP16 读取在同一输入线程，CPU 转换 |
| **FP16 输入线程连续工作合计** | — | **8.50** | 上面两步串行 |
| 运动估计整体 | 13.38 | 12.03 | 独立运动线程，NVENC 代理 / 软件解码 / 向量归约；MP4 的 GPU NV12 转换在此行内 |
| **主编码流程整体** | **14.80** | **14.20** | 主编码线程；含模型、参考平移/更新、周期参考重建及熵任务提交，不含异步熵编码 |
| 其中主编码模型 GPU stream 时间 | 13.09 | 12.87 | 包含在主编码流程中，不可重复相加 |
| 其中参考平移墙钟时间 | 0.41 | 0.28 | 包含在主编码流程中 |
| 其中参考特征 GPU 缓存更新 | 0.18 | 0.07 | 包含在主编码流程中 |
| CPU 熵编码 | 5.37 | 6.45 | 独立熵线程 |
| 文件码流输出 | 0.046 | 0.044 | CPU 写入，没有 PNG/RTSP 输出 |

模块是多线程流水线，不把各行总耗时相加来估计 FPS。理想情况下，流水线吞吐受最慢的**连续工作阶段**约束：

```text
理想流水线 FPS ≈ 1000 / max(各独立阶段的 ms/帧)
MP4：1000 / (9.45 + 13.47) ≈ 43.63 FPS
FP16：1000 / 14.20 ≈ 70.43 FPS
```

| 输入 | 瓶颈阶段 | 瓶颈均值 | 理想流水线 FPS | 同轮计时版实际 FPS |
|---|---|---:|---:|---:|
| MP4 | 视频读取 / 解码 / BGR 转换 | 22.92 ms | 43.63 | 43.51（43.41 / 43.21 / 43.92） |
| FP16 | 主编码流程 | 14.20 ms | 70.43 | 69.67（69.87 / 69.54 / 69.58） |

这是一阶平均吞吐估算，不是所有视频/负载下的保证。阶段可能共享 GPU、内存带宽和 CPU，周期重建、队列、同步及调度会降低实际吞吐。只看模型 GPU stream 的 13.09/12.87 ms，会得到约 76/78 FPS，但这个数没有包含完整编码流程。

MP4 输入消费者的队列等待约 15.73 ms，已经在外层 `video.read.frame` 的 16.38 ms 内。这是等待上游供帧，不能作为新的串行模块再加到 22.92 ms 上。GPU stream 计时包含 enqueue 间隙及其他工作干扰，不代表纯 kernel 时间；主编码里的约 11.8 ms CUDA fence 等待与约 13 ms GPU 推理重叠，也不能相加。

Nsight Systems 在启动 3 秒后采集 4 秒 CUDA 时间线：MP4 的 GPU kernel 时间区间覆盖率约 61.7%，FP16 约 90.5%。这不是 SM 利用率，也不含 NVENC 硬件引擎，作用是佐证 MP4 仍在等 CPU 供帧，而 FP16 接近当前 GPU 编码流程的吞吐上限。当前优先优化点是 MP4 后端解码及 BGR 中间格式转换；FP16 则应针对模型执行和主编码流程继续优化。

## GPU 参考缓存入口修正与验证

入口修正后，profile 明确出现 `reference.store_feature_wall`，并记录每帧跳过 `MLVCEncoder.feature` 的 CPU materialization；此前这些记录不存在。MP4 主输入已在 GPU，FP16 文件输入仍需要 CPU→GPU 上传；`input_x_h2d_bytes` 只计 TensorRT runtime 自己执行的上传，GPU 输出绑定模式下还可能由 stage input workspace 执行上传，不能把该计数 0 解释为所有输入没有 H2D。

同配置计时版，入口修正前 FP16 为 66.02 FPS、修正后为 69.67 FPS；主编码流程 14.91→14.20 ms。早先业务程序的 FP16 三轮约 64.40 FPS 是此前版本/运行状态的测量。最新数值来自修正后的版本，不能混为同一个版本的重复测试。

CTest 12/12 通过。修正后 MP4 / FP16 的六次完整文件输出逐比特一致；分别通过 RTP 将 537 帧发送到原解码程序所在板卡，均全部解码。无详细计时的单次 RTP 回归为 MP4 编码 45.34 FPS、FP16 编码 69.41 FPS，这些单次值只作回归记录，不替代上表同轮三次均值。

详细探针通过 `MLVC_THOR_TIMING=1` 启用，`MLVC_THOR_TIMING_WARMUP=96` 控制逐标签排除的预热样本；默认关闭，不添加额外 stream fence。输入和 TensorRT 用复用的 CUDA events，在已有同步点后读取时间。常规 Chrome trace 与 `tools/analyze_module_timing.py` 可复现统计。Nsight 单独运行，没有与正式计时或质量测试并发。
