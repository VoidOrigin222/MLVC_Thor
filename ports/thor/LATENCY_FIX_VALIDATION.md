# 五路时延积压修复（2026-10-16）

## 问题与计时口径

此前约 336–345 ms 是 2026-10-14 两轮测试的最后 120 帧均值；2026-10-15
约 3967 ms 是去掉前 96 帧后的全窗口均值。窗口不同，但也存在真实退化：
10 月 15 日各路最后 120 帧仍为 4468–5728 ms，并非仅由统计口径引起。

本次重新运行未修改的 a2422ce 程序复现：全窗口均值 4235 ms，最后 120 帧
合并均值 6123 ms。每路接收队列峰值 59–71 帧，编码侧准备到输出均值仅约
339 ms，主要积压位于解码侧消费不足后的 RTP 接收队列。

输入仍是同一课堂视频五个时间偏移的 1920×1080、13 FPS H.264 RTSP，目标
每路 12 FPS，QP=11，GOP=96，reset=32，熵窗口 1，RTP 完整验帧 fail。
12 FPS 每帧周期约 83.3 ms；旧解码模型提交到完成平均约 82.4 ms，叠加参考处理
等步骤后只能处理约 10.7 FPS/路，无法持续追上源。扩大队列只推迟溢出。

以下时延始终使用同一编码板时钟上的“NVDEC 读帧就绪 → 收到解码完成回执”，
不包含曝光、上游 RTSP 缓存、NVENC 发布完成及浏览器显示，不能称为完整显示时延。

## 修改

1. TensorRT 单上下文模型默认用 CUDA Graph 重放。每个上下文保持固定 GPU I/O
   地址，调用方轮换缓冲通过显式复制接入，避免重放图访问错误或过期的地址。
   捕获不支持时记录原因并回退普通 enqueue；可用 `MLVC_THOR_CUDA_GRAPH=0`
   诊断。batch5 仍走原批调度器。
2. 解码参考平移缓冲改为每路持久复用，消除原先每帧 cudaMalloc/cudaFree。
   平移 kernel 及同步改用所属路的计算流，取消五路共享默认流的等待。
3. 重建 NV12 直接送入 NVENC GPU 帧，取消设备→CPU→编码器的整帧往返。
   NVENC 使用独立的非阻塞复制流，并在送编码器前只等待本路输入复制完成。
   为维持编码器帧所有权仍保留必要的 GPU 内部复制，不宣称完全没有复制。
4. 基准脚本支持循环素材及自定义长轮超时，回执和遥测采集器同步延长。
   回执不完整时不再把早期的“最后 120 个已收到样本”误当作真正末尾 120 帧。

固定上下文状态及 I/O 地址遵循 [NVIDIA TensorRT CUDA Graph 约束](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/optimization.html#cuda-graphs)。
本次没有更换引擎、QP、分辨率、目标帧率或通过丢帧清理队列。

## 回归与短轮结果

- CTest 15/15 通过，新增平移缓冲复用及非默认流检查，覆盖边界和平移重叠输入。
- 三个真实 TensorRT 模型各 4 个不同输入/QP/参考特征的普通提交与图重放输出逐字节一致；
  包括捕获后改变调用方地址及 CPU/GPU 输入输出，确认确实执行图重放。
- 长轮超时、缺失末尾回执、连续时间戳发布源的三个测试通过。
- 完整修改的五路 780 帧/路测试，3900 帧全部编码、解码、回执、NVENC 发布，
  接收丢包、队列丢帧、CRC 错误、依赖缺口和发布丢帧均为 0。

| 版本，均为 780 帧/路 | 全窗口均值 | 最后 120 帧合并均值 |
|---|---:|---:|
| 修改前 | 4235 ms | 6123 ms |
| 第一阶段：图提交与 GPU NVENC 输入 | 2099 ms | 2630 ms |
| 加入持久平移缓存与独立流 | 745 ms | 264 ms |

短轮修复后各路尾部均值 255–274 ms，尾部回执约 12.03–12.14 FPS/路；
启动后仍有暂态积压，随后消化，因此不能把 264 ms 写成全程平均值。
解码模型 runtime 墙钟均值约 82.4→55.1 ms，提交 API 约 18.4→0.18 ms。
这些时间含并发竞争和同步，不等于纯 GPU kernel 时间，流水线各步骤不能直接相加。

## 长轮结果

修正测试源后的连续 260 秒测试为每路 3120 帧，五路共 15600 帧，编码、解码、
回执、NVENC 发布数全部一致，接收丢包、队列丢帧、CRC 错误、依赖缺口和发布
丢帧均为 0。五路 NVDEC 读帧记录的 PTS 均严格递增。

排除每路前 96 帧，全部 15120 个逐帧样本按同一时钟统计：

| 窗口 | 平均 | P95 | P99 | 最大 | 时延标准差 |
|---|---:|---:|---:|---:|---:|
| 全统计窗口 | 275.2 ms | 372.8 ms | 420.4 ms | 1019.8 ms | 53.5 ms |
| 最后 60 秒，3600 个样本 | 273.1 ms | 371.1 ms | 406.0 ms | 494.8 ms | 46.7 ms |
| 最后 120 帧/路，600 个样本 | 270.9 ms | 362.6 ms | 413.6 ms | 427.8 ms | 45.9 ms |

接收队列峰值每路 7–12 帧，包含启动暂态；没有后期持续增长至数十帧的现象。
短时尖峰仍存在，不能声称每帧都小于 300 ms。分位数采用排序样本的线性插值，
标准差为总体标准差，全部高时延样本保留。

首次长轮 5×3120 帧均完整发布，但回执采集器沿用 90 秒默认值，仅保存了每路
989 个回执。该轮 `complete=false`，未用于末尾时延结论；修正采集器后重跑。
原始失败采样与完整重跑均保存在本地，不隐藏或补造缺失回执。

补齐回执后的下一轮有中途短时峰值。逐帧分析发现测试发布器实时 stream_loop
叠加各路 input seek 后，在循环处出现连续重复 PTS，随后突发送帧；单路读帧速度
短时超过 20 FPS，加重了其他路的 GPU 竞争。这不是恒定 13 FPS 的输入条件。
该轮完整保留为 `fixed-long2.json`，不作为恒定源的稳定性结论。
修正发布器后，先复制展开 345 秒素材，4485 个输入包 PTS 严格递增，再实时
发布五路。生产编码器及实际编解码帧数不变，没有在测量中删除高时延样本。

## 复现与边界

```powershell
python ports/thor/tools/benchmark_five.py --scheme contexts --frames 3120 `
  --target-fps 12 --decoder-entropy-workers 1 --binary-dir bin `
  --timeout-seconds 330 --loop-input --label latency-check `
  --output artifacts/latency-check.json
```

MediaMTX 与测试素材按 [基准说明](BENCHMARKING.md) 准备。测试程序先使用
`bin/latency-test`，确认通过后同步到两板的正式 `bin/`，旧程序保留备份。
完整结果、逐帧统计摘要、构建/测试日志及程序归档在本地
`artifacts/latency-fix-20261016/`。帧时延标准差包含排队变化，不是 RTP 包抖动。

没有锁定 GPU 频率；不将单个子改动的耗时差当作独立因果收益。验证仅覆盖本次
视频及有限时长五路测试，不扩展为真实便携终端、目标识别或任意场景长期保证。
