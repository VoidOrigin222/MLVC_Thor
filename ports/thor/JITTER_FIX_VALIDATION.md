# 五路积压与时延抖动修复（2026-10-17）

本记录保留当日同素材测试结论。10 月 18 日混合五路的 GPU 调度、输入复制及
CUVID 显示缓冲修复见 [混合五路验证](MIXED_LATENCY_VALIDATION.md)。

## 测量范围

双 Thor，五个独立 TensorRT 上下文，RTSP/NVDEC 输入、语义 RTP 传输、
NVENC/RTSP 发布。输入和输出目标均为 1920×1080、12 FPS，QP=11、GOP=96、
reset=32、LTR 关闭，解码熵窗口为 1。不改变引擎或压缩参数，不用丢帧追赶。
五路是同一矿井素材的五个时间偏移，不是五台独立便携终端的验收。

时延沿用编码板同一单调时钟上的“NVDEC 读帧就绪 → 收到解码完成回执”。
不含摄像头曝光、上游 RTSP 缓冲、NVENC 发布完成和浏览器显示。抖动分别列出
时延标准差与同一路相邻帧时延差的绝对值，不能混用两种定义。
`decode.frame.start/complete` 覆盖整帧处理，包括模型、参考更新和输出入队，
不是单独模型的 kernel 时间；末包接收到 start 的一段包括排队和 CPU 熵解码。

## 积压位置

10 月 16 日 12→12 FPS 长测记录中，动态场景帧 130 的约 1517 ms 可拆为：
编码侧就绪到首包约 716 ms，分片发送约 4 ms，发完到回执约 797 ms。
静态峰值也同时包含编码预取与解码侧等待。它不是单次模型推理花了 1.5 秒。

本次先保留旧程序复现。390 帧/路诊断轮中，第二号路帧 360 达 3251 ms：
编码侧 359 ms，分片发送 3.7 ms，解码板末包接收到发回执 2887 ms，
剩余网络与回执开销约 0.15 ms；接收队列全轮最高 33 帧。后两段使用解码板
本地单调时钟相减，不依赖双板墙钟同步。该轮长度与旧长测不同，只用于定位，
不能直接作为同窗口性能对照。

发现三个来源：

1. 模型首次执行、CUDA Graph 捕获和五路上下文初始化与实时消费重叠，启动时
   形成 FIFO 欠账；没有丢包也可能要花数秒消化。
2. 通用 RTSP FPS 探测、4 帧采集队列和 2 帧运动预取增加在途帧数。每路
   12 FPS 下多等一帧就是约 83 ms。
3. 单 worker 熵窗口提交当前帧后，要等下一帧或 EOS 才取出结果。输入间隔会
   直接进入当前帧时延；遇到输入暂停还会推迟已经可解码的帧。

## 修改

- 所有单上下文模型在接收实时帧前执行三次准备推理，完成惰性初始化和图捕获。
  `Prepare()` 幂等，准备数据不参与实际参考状态；真实输入覆盖固定 I/O 缓冲。
  五路运行时构造串行化，随后保留原启动栅栏和独立执行流。
  `MLVC_THOR_PREWARM=0` 可用于诊断；batch5 路径不执行这项准备。
- RTSP FPS 通用探测关闭，仍用前五个已解码 PTS 推导源帧率；这五帧保留。
  analyze/probe 上限缩为 250 ms/256 KiB。没有启用会丢弃探测包的 NOBUFFER，
  避免丢掉首个 IDR 后等待下一次长 GOP。
- 实时采集队列由 4 帧缩为 1 帧，先等队列空间再读取 NVDEC；文件路径仍为
  4 帧。contexts 五份编码配置的 `motion_prefetch_frames` 从 2 调为 1。
  没有覆盖旧帧或重置源时间戳，另行检查 PTS 相对读取时钟是否持续落后。
- Thor 单 worker 在有界、有序的 packet processor 阶段提交熵任务及其 future，
  再由 consumer 取出结果、执行 GPU 帧处理。当前结果不等待下一帧或 EOS，同时允许下一帧
  CPU 熵解码与当前 GPU 帧重叠。该路径强制单个 packet processor 独占熵槽 0，
  避免多个 stream worker 并发使用同一熵解码器。异常仍在 consumer 的 `get()`
  处抛出，取消时未消费的 future 等待任务完成后才释放熵解码器。原有队列预算仍生效；
  多 worker 熵窗口和 Ascend 的消费策略保持原行为。
- 开启 profile 时新增带帧号和单调时钟的解码开始、完成事件，配合实际 RTP
  收发观察记录区分排队、处理与链路开销。未开启 profile 不增加这两项事件。
- 熵表在等待流头之前完成加载；Thor 的输出 NVENC 构造与 GPU 表面分配改在
  帧处理流水线启动前执行，避免首帧发布时的惰性分配干扰其他路推理。
  没有送入虚拟编码帧，真实首帧仍以 NVENC 序号 0 开始；准备开销分别计入
  `decode.setup.entropy` 与 `decode.setup.nvenc`，不把前移工作说成消除了工作量。

## 逐步验证

以下短轮同用动态素材。旧程序轮为 390 帧/路，其余为 780 帧/路；表中只统计
每路帧号 ≥96，逐步轮用于判断修改方向，不替代最终同长度长测。

| 修改阶段 | 平均时延 ms | P95 ms | 最大值 ms | 时延标准差 ms |
|---|---:|---:|---:|---:|
| 旧程序诊断轮 | 1814.9 | 3085.8 | 3250.6 | 581.9 |
| 仅准备模型 | 1016.3 | 1336.6 | 1677.5 | 190.3 |
| 加缩短探测与采集队列 | 475.3 | 965.5 | 1195.3 | 249.9 |
| 加单 worker 即时消费 | 203.7 | 443.3 | 584.3 | 90.2 |
| 加运动预取 1 帧 | 164.8 | 224.3 | 328.6 | 30.3 |

最后一轮编码 FPS 为 11.978–11.988。解码板末包接收到回执的稳定窗口均值
55.1 ms、P95 86.3 ms、最大 169.9 ms，网络与回执剩余开销均值 0.34 ms。
全窗口仍有 1071 ms 启动峰值，不能把稳定窗口的 329 ms 说成全程最大值。

**这个串行消费候选版在后续长测中未通过峰值检查，因此没有作为最终部署版。**
动态 3120 帧/路长测的全窗口最大值仍达 1662 ms，帧 102 中约 1296 ms 发生
在解码 GPU 帧开始之前，当前帧处理约 60 ms。帧 32–95 的每帧处理平均约
79–80 ms，帧间串行熵解码约 12 ms，合计超过 83.3 ms 帧周期，启动欠账
一直延续到帧号 96 之后。只看 780 帧短测无法排除这种启动差异。
对应静态长轮在更换流水线方案后主动停止，其不完整记录保留且不计入最终结果。
最终实现改为上述 packet processor 与 GPU consumer 重叠。
中间一次 processor 内等待 future 的动态轮也在改用 consumer 传播异常后主动
停止；该轮不完整、只用于开发观察，不计入最终长测。

future packet 版本的第一组长轮（r7）已把帧号 ≥96 的平均时延降到静态
171 ms、动态 183 ms，但仍有静态 1428 ms、动态 1122 ms 的启动峰值。
静态最坏帧 18 的解码板驻留约 1151 ms，其中帧处理前约 1072 ms、当前帧处理
约 78 ms。因此继续将熵表和惰性 NVENC 初始化前移，最终长轮采用 r8。

另做五路单帧活性验证：编码只发一帧，解码 `frame_num=-1` 等待 EOS，观察器
把编码 EOS 发出延后 2000 ms。旧版本回执比 EOS 晚 23–54 ms，新版本回执
比 EOS 早 1677–1921 ms，证明不再等下一帧或结束包。最初有限帧数的试验会
由帧数边界触发 drain，不能验证此问题；`frame_num=0` 为非法配置的失败记录
也保留，最终判断采用旧版 `eos-live-old` 与最终初始化前移版 `eos-startup` 两轮。

## 回归及证据

- CTest 15/15 通过。
- 五路短流故意跳过参考帧，验证 consumer 报错后的取消与 pending future
  释放：五路均因预期的 short reference 错误退出，无挂住或崩溃。
  最初短流试验误用 96 帧 warmup，被参数校验拒绝；改为 warmup=0 后重测通过，
  两次试验日志均保留，参数错误未计为业务失败或性能样本。
- 三个真实模型各四组不同输入、QP 和非零参考特征，在未准备的普通执行和准备后的
  CUDA Graph 路径输出逐字节相同；覆盖调用方地址轮换、CPU/GPU I/O，验证
  重复准备不再次运行或捕获模型。
- 修改的 C++ 文件通过仓库 clang-format 检查。cpplint 沿用项目过滤项，另外
  过滤既有 SHA-256 常量数组被误判的 `whitespace/indent_namespace`。
- UI 精简及 EXE 验证见 [UI 验证记录](../../tools/ui/VALIDATION.md)。
